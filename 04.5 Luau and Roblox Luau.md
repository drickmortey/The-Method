
Let's make a pile of parts that keeps on collecting.
```lua
while true do
task.wait(.01)

spawnPart()
end
```

Should work, right?

Maybe in Roblox Studio, if you have a function called `spawnPart()`, but not in *standalone* Luau (the one on Luau Playground). This is because they are not the same. They aren't embedded the same way.

An obvious difference is that you don't have the Roblox engine at your disposal. Something less obvious is that you don't have any way to put waits in your code.

## Why this is the case
What is a programming language good for if it doesn't have something as basic as waiting? We could make our own wait (though it'd be horrendous), how is Roblox's so performant? Let's look into how a wait really works.

First, our garbage version of wait:
```lua
local function wait(waitFor)
local now = os.clock()
--this works because execution will not leave
--the loop until the loop is broken
--when the time has elapsed
repeat until (os.clock()-now) >= waitFor 
end

wait(3)
print("Hello *wink*")
--this works, you can test
--additional delay may be incurred
--because of compilation
```
It works, what's wrong here? This kind of waiting is called **busy waiting**, it's widely considered a bad thing. It's essentially making your CPU spend resources on doing nothing until the time has elapsed. The way `os.clock` works is that every time your CPU actively does something, it takes the time it took to do that and adds it to the "clock" (we can fetch this with `os.clock()`). This time is in seconds. Basically we're setting the CPU's focus and utilization on doing nothing (busily).
> os.clock doesn't include time spent doing nothing meaningful, so it's good for benchmarking code.

> os.clock (in Studio) starts counting time the moment Studio is started. You'll see the same os.clock time across the client and the server because your device is simulating both in Studio (this wouldn't happen in a real session).

> On Luau Playground however, the clock is reset every time you run your code. You can observe as the clock time on studio keeps adding up even when not in a game or in a playtest. There's many of these subtle differences between Roblox and "standard" Luau.

Now let's observe the wait of Roblox. There's two available for you.
```lua
wait() --the old classic
--this uses the old roblox scheduler

task.wait() --the newer, better one
--this waits in a different and unique way with more accuracy. this uses the new roblox scheduler
```
> The new scheduler is improved and optimized for modern hardware, so there is realistically no reason to use the old `wait`.

> The old scheduler made it so that `wait` was subject to *throttling*, which was a limit on how many times per second a thread could be checked to wake up. It could at most check 30 times a second, throttling well below this under load.

> The new scheduler is designed in a way that avoids throttling entirely. `task.wait` is tied to `RunService.Heartbeat` (that targets 60fps) and waits much more accurately than `wait`, which could overshoot the target time under load. Clients can increase their fps cap to go above 60fps, the changes can be observed in `RunService`.

Right now, the definitive way to do waiting is with `task.wait`, part of the `task` library. You'd notice that the `task` library does not exist in browser Luau (I'll call it that). This is because Roblox has something called a **scheduler**, the `task` library is based off of said scheduler. 
> A library is a collection of related functions for a particular purpose.

A schedule is a plan that defines when you're going to do something. It has a proper order to it, this before that. You can add stuff to the schedule as your day goes on. You're keeping a record to stay punctual and *on-time*.

This is basically the scheduler's job. Internally, there's one CPU core designated to run your programs (can schedule tasks to multiple cores with Parallel Luau). It can only do one thing at a time, so it schedules things based on the data it has and how important your task looks. The scheduler provides us with access to *time* and **sleeping**.

You heard me right. Sleeping is the opposite of busy-waiting. Instead of intentfully and furiously standing around, you could just sleep. No energy wasted. 

All of your code is in a list of tasks called a **thread** (the thing that's being scheduled). When your program tells the scheduler "I'm gonna sleep for this much time", it puts the CPU's focus on other threads and leaves the one that requested sleeping for the amount of time it asked for.

## How does it know the time's up?
Aren't we just checking the time repeatedly here too? Kind of. 

The scheduler runs every frame, doing time calculations along it. This is kind of misleading, because the scheduler does decide when each frame starts and ends. In fact, it provides us with a useful scheduler-based service called `RunService` in Roblox. This contains API to interact with the scheduler (e.g. to run some code every frame, detect if the scheduler is in a client or server environment, etc).

When scheduling, it has a small step for waking up threads whose alotted time has elapsed. This is tiny compared to the other things it has to do on a per-frame basis. `task.spawn` is another extremely useful function inside the library. It is impossible to make a coherent game without a scheduler managing the threads and doing timekeeping.

The old scheduler used this basic principle of checking whose time is up every frame. The new one fundamentally does this too, but more efficiently by determining which threads have more priority.

> The scheduler usually targets 60hz, but another part of it targets 240hz for physics simulation. That's 240 times per second.

Thus the reason why browser Luau doesn't have any waits or `task` library functions is because those rely purely on a scheduler that it doesn't have.

All you really need to do is provide Luau with a scheduler, and then using that scheduler, these capabilities are very possible. We need to host Luau in something that does this.

Check this

https://github.com/luau-lang/lute

Lute is a runtime for Luau. It comes with everything, even a scheduler. It's designed to be similar to Roblox and its API. This makes Luau general purpose. It's built and maintained by the Luau team.
> Runtime in this context means the entire system that Lute provides that code needs in order to do stuff beyond the abilities of the language alone, like scheduling threads. With this runtime, Luau can make http requests and interact with system files.

## Another way Roblox Luau is different
If you remember the third article, I mentioned that we need the `--!nocheck` file directive before declaring global variables due to a warn that Luau Playground produced. Why doesn't this show up in Roblox Studio?

The warn is telling you that a local variable undoubtedly works better in your use case. Why is the language more lax in Studio? The **linter** in (browser and Studio) Luau are tweaked differently.

The linter is a software that reads your code while you're writing it in order to make suggestions and warn against bad code practices. There's a whole list of possible warns. The linter is NOT the typechecker, that is a separate thing. You can turn off linting with `--!nolint` (generally not recommended). You can disable a warn by name with `--!nolint IDENTIFIER`. Warn names are in `PascalCase`.
> View all the possible linter warns here https://luau.org/lint/

While browser Luau has all the warns enabled, Roblox has some disabled to keep the warns less annoying (like the very first warn mentioned in the list, the one we faced). Roblox has enabled all the warns that are relevant.

An easy way to distinguish linter warns from type errors or normal errors is to hover your cursor over the erroneous material and check the name of what's popped up. You might see `Syntax error:` (meaning you typed it wrong), or `type error:` (usually due to type mismatches between operands). But if it is something oddly specific like `UnknownGlobal:` or `ComparisonPrecedence:`, it's a linter warn.

Unlike the typechecker, the linter is more "innocent". Its job isn't to annoy you and make you miserable, but to point out semantic and structural problems in what you're doing (though you might want to shut it up if you're doing it intentionally).

Let's try an example where you do something the linter warns against, but you do it on purpose:

```lua
--"do return end" is commonly used for debugging (Lua manual mentions it)
--it stops execution past a certain point
--I use it sometimes

local function broken()
local array = {1,2,3}

    do return end
    --never reaches here
    --the warn here is called "UnreachableCode".
    for i, v in ipair(array) do 

    end
end
```
