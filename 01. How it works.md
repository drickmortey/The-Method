# What is scripting, really?
<p>
Scripting IS programming, but a special kind at it. 

It's the process of controlling another program via "scripts", this program in our case being the Roblox engine. Think about it, the Roblox engine has 3D graphics, online multiplayer, physics, it's a huge thing. With only Luau and no engine, we're practically in a void. We can't do anything useful other than use the limited stuff that Luau itself comes with. We need the Roblox engine to extend our functionality.

E.g. Luau doesn't really have a way to create a part in the world, we must use what control Luau gets of the engine to do that. This is called **Engine API**, you can view the entire list of what's included right here at https://create.roblox.com/docs/reference/engine. Seriously it's a gimongous list.

> API stands for Application Programming Interface, it's a way that something with more control gives us access to it for a particular purpose.
</p>

# Why Roblox chose a scripting language
<p>
You'll sometimes hear people say that scripting languages are ultra slow compared to "programming languages" (they are mainly referring to C or C++), in a nutshell this is true, but that's not the whole story. So why a scripting language?

Let's not discredit Luau, it's pretty fast. It's also just what Roblox needs, its implementation as a scripting language makes it so that it isn't the boss around the place. It needs another program to control, what that program is written in is called the **Host language**. Roblox in particular, C++ hosts Luau. 

### So why not let me use C++ if it's so good???

1. It gives the programmer too much control, Roblox games are supposed to come malware-free and threat-free.. Other than that, you can do really stupid things. One of its design principles is to let the programmer do *whatever* they want. This is not what Roblox wants!

2. It's simply a very complicated language. Its bar of entry basically excludes children.

3. There's a lot of things in the engine that you have no business in. You decide what a scripting language sees, its abilities mostly constrained to what API you expose to it.

4. Many scripting languages (especially Luau) have simplified programming and have hidden the complexities so you don't shoot yourself in the foot. You don't have to think about freeing memory, not adding things into arrays past their size, or which of the 4 or 5 ways you should initialize your variable (I can't even remember).

> Luau is a high-level language, this doesn't mean it's hard to understand. This means it's far from hardware with the amount of simplifications (or in technical terms, "abstractions") that it has. You don't have to face many weird computer gimmicks. C++ is considered middle-level, though by today's standards some call it low-level (not true but alright). Assembly is undoubtedly low-level, and the closest to hardware is machine code (binary).

5. Portability. Your code is first translated into *bytecode* instead of direct machine code. Why? Machine code can only run on one platform, the one that it was compiled for. This is a weakness, we don't want to recompile (retranslate) our code for every change we make to it, repeat for every platform. We can translate into bytecode once before the game runs, and use a special program (Virtual Machine) to tell us what the bytecode means in machine code for the user's platform. This behaviour is commonly associated with scripting languages. (P.S all code is translated into bytecode before running it)

## And the main reason!

6. Running your code is actually not that expensive. The rest of the engine utilizes the power of C++, which does the bulk of the work (e.g. updating physics 240 times a second). Code performance usually isn't a big deal, the bigger concern is what your program causes for the engine (creating 1000 parts in a second is "easy" to execute, but?). Another point, using the engine API runs C++ code that the Roblox team wrote and optimized heavily (usually). So even if Luau was twice as fast, it wouldn't nearly make all your code twice as performant.

### What if I really need the performance?

Sometimes yeah, you could use more metal. Your code will only run on a single CPU core, which is rarely a problem (this is a deliberate design choice, trust). Roblox has provided Parallel Luau to utilize more cores if you need, along with other tools. If you're optimizing for mobile, the physical world is usually the kidney stone because unoptimized builds can hog up RAM and choke the small little graphics card. *This doesn't give you a pass to write abhorrent code by the way*.
</p>

# EXTRA: Compiled vs Interpreted languages
<p>

People usually say scripting language = Interpreted language. This isn't true, it's just an engineering decision. Scripting languages *can* and have been compiled. Interpreting a scripting language actually creates one of its biggest selling points, which is why Lua and Luau are interpreted in most implementations.

### Compilation

Compilation is when code is translated directly into machine code, at the end of which an executable (.exe on Windows) is created. You can run this by double clicking it in file explorer.

Pros

- Direct machine code is very fast, especially for good quality reasonably-optimized code. The instructions target a general CPU architecture and are thus efficient. Standard compilers in the GCC (GNU compiler collection) are made by experienced software engineers so that even bad programs can be fast-ish.

- Because all of your program is known at the time of translation, stricter optimizations can be applied. Modern compilers recognize patterns and employ a much more efficient way that doesn't do exactly what your program describes but mimics it so that the end result is the same in less work.

- Better analysis on your program than interpreted languages. Any standard compiler will run extensive checks on your code to give any warns (e.g. blatant bad practices) or describe an error in detail. Development environments like Visual Studio Community have built-in compilers with many settings to diagnose and run icky code (e.g., treat warns as errors, higher levels of checks).

> A development environment is more technically called an IDE, or Integrated Development Environment. Normally, you'd need a text editor to write code, a program on the side to run and test it (maybe you need to compile it first), you'd want your code to have proper highlighting to better read it, etc etc. Having all of these separate makes development tedious, an IDE puts them all together in one place to make your work easier (integrates them into.. one development environment). Your IDE in Roblox is the script editor, but you can connect an external one through an MCP server.

- You do not need an interpreter or fancy setup to run this code, you just run the executable that's generated...

Cons

- The compiled code will only work for the platform it was compiled for. Trying to run it on a machine it wasn't intended for can be dangerous, the CPU doesn't check the validity of the instructions it executes. Though there are some safety mechanisms in place in the modern era. 

- You need to recompile the code every single time you're done making changes to it. This can take a long time if you have a big program (the Roblox app is more than one million lines of C++ code, not including the game client). With context, smart compilers can avoid a lot of recompilation work. So.. instead of just pressing the "run" button to test your new code, you need to run it through a compiler again.

> This means every time Roblox releases an update, they have to recompile their mega codebases for every single platform Roblox is on. Now they're not pressing the compile button 5 times, their workflow is more sophisticated and automated.

- Not a huge problem usually, but compiled code takes more disk space than bytecode that is interpreted.

---
### Interpretation
Interpretation is the process of reading bytecode, finding out what machine code represents it best, and running that. This is done for every statement that's being interpreted. Sounds slow? Kind of is. But computers are pretty fast. Your code is always first turned into bytecode before running. A lot of people think the "interpreter" and the "VM" are separate, when they are the exact same thing.
> You can find what bytecode your program translates to by clicking the `Bytecode` button in the top bar at https://play.luau.org.

> For VMs, reading bytecode is much easier than reading raw text because a lot of the work has already been done and the instructions are more straight-forward. You can think of bytecode as the in-between of your code and machine code.

> JIT (Just-In-Time) compilation in an interpreter keeps a track of code that runs repeatedly and decides if it should be compiled to machine code for ez wins, but Roblox Luau doesn't use this for multiple reasons whether you like it or not. Emphasis on "Roblox Luau" which we will discuss in a later article.

Pros

- Code doesn't need to be retranslated for every change, it will run as long as the VM knows how to give machine code for your device's platform (the main selling point).

- In Roblox scripting, this means that you can test and tweak your code easily without raging over compilation times when your program gets a bit long.

- The same bytecode will work on every platform the VM supports, this is portability (working properly on different platforms). This is huge for Roblox devs if you can't tell.

- Not a lot of performance loss is incurred because all the engine API (the expensive stuff) runs compiled machine code, the cost of running Luau itself is "minimal".

Cons

- REALLY slow compared to alright-to-good compiled code, though as I said the loss isn't anything to cry about.

- Finding faults depends on if your code experiences an error while translating to bytecode or if it has an error while running it (e.g. bytecode expected the thing you're accessing to exist, but it doesn't). This "auto" analysis is not as extensive as when a compiler runs a full investigation on your faulty code before anything is run. This is because everything is known during compilation time, however some things aren't known until running the code in interpreter setups.

> Luau implements the type system to help improve your code comprehension and avoid problems by creating warns whenever it detects sonething isn't right. Many find this very annoying and sometimes turn it off, but this is beneficial to those who know how to use it properly. Anything in your code pertaining to types (definitions, annotations, casts, etc) is completely stripped off before turning it into bytecode, it only exists for the programmer's convenience. Luau can give you convenient autocomplete and tell you all about a piece of data if it knows the types properly.


We'll discuss the type system in detail in the future, it's almost what Luau is known for vs Lua. It might ruin your life or you'll find peace in it if you tame it.

</p>

# Extra 2: How was the first compiler made?
<p>

Long ago in the dark ages, computer scientists had computers the size of a small bedroom you'll get in a budget NY apartment for 2000$ a month. Though they didn't have to keep recompiling their code like the standard sheeple (who didn't exist at the time). In fact, they had to input direct machine code. You *were* the compiler. And yes this was very insufferable and prone to error, you would need to remember specific combinations of ones and zeroes (which would correspond to a CPU instruction). The computer scientists of course didn't enjoy this part of their job very much. They wanted a way to **simplify** programming.

Eventually, after working with sticks and stones, they got tools. Somebody created an assembler (where we get "assembly" from). This was a huge simplification, instead of ones and zeroes, you could finally write a human-readable word. These simplifications are called abstractions. We can say that assembly abstracts machine code. An assembler was practically the first compiler, it translated assembly into machine code.

> There are multiple assembly "languages", every CPU architecture has its own assembly. Assembly basically lets you work with CPU instructions as words (translated by an assembler), and so the assembly of a CPU depends on its instruction set. x86 assembly is of Intel's old 32 bit processors, x64 is the assembly of most modern 64 bit processors, and ARM is the assembly of power-efficient processors for things like phones.

The invention of assemblers made it much easier to create more sophisticated programs. This allowed the creation of better and more convenient **Graphical User Interfaces**, or GUI. In standard computing terms, this takes you from programming on "bare metal" or in a bad text editor to an application thing with buttons and shapes. These evolved into IDEs, with proper development tools built into them.

Assembly was used to make more "abstract" (or, simpler) programming languages. An early one was B, which turned into.. C. The first version of C was made primarily with assembly. Its compiler was made with assembly too. So the assembler was used to create a proper compiler.. This is called **bootstrapping**, creating more powerful tools with simpler ones. This started the "compiler compiles the code for another compiler" chain.

When C got good enough, its compiler was rewritten in C. And guess what, it was compiled by that older compiler!

</p>
